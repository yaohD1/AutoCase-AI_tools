# RF 关键字索引器 —— 真实项目文件验证

> 2026-10-26。用项目里真实的两份业务关键字文件（`操作日志.resource` / `安全日志.resource`，已脱敏）验证索引器，
> 回答一个问题：**这套「索引给上下文 + agent 写脚本」的路线，在真实 RF 代码上站不站得住。**

## 0. 验证对象的性质

这两份文件不是玩具样本，它们暴露了真实项目的四个特征：

| 特征 | 实例 |
|---|---|
| 中文跨层级引用 | `Resource  ../../../元素定位层/日常运维/日志管理/操作日志页面元素.resource` |
| 变量层与关键字层分离 | 关键字体内全是 `${操作日志列表的用户名称}`，定义在另一个目录 |
| 变量文件混用 `.py` | `Variables  ../../../测试数据层/公共数据.py`，`${hostIp}` 来自这里 |
| 注释掉的定义 / 调用 | `# 进入安全日志三级菜单`（整段注释）、`#操作日志列表加载完成`（单行注释） |
| 近义变体共存 | `操作日志列表断言` vs `IMS操作日志列表断言`，只差来源 IP 默认值 |

元素定位层和 `.py` 变量文件是我按被引用的名字补齐的**脱敏替身**（真实文件未提供），
所以本报告里"变量可溯源 100%"证明的是**机制可行**，不代表线上覆盖率。

## 3. 补强一：变量溯源（0% → 100%）

初版索引器只解析 `*** Keywords ***`，`*** Variables ***` 和 `Variables ...py` 完全没碰。
后果：交付给模型的签名里带着 `${hostIp}`、`${操作日志列表的用户名称}` 这类**来历不明的符号**。

补上两件事之后：

```
关键字体内引用的变量: 38 个
能定位到定义来源: 38 个 (100%)
```

```
${操作日志列表的用户名称}
    元素定位层/日常运维/日志管理/操作日志页面元素.resource
    xpath=//div[@class='log-table']//tr[1]/td[2]
${hostIp}
    (.py 变量文件)
    "10.10.10.1"
```

价值不在"能读出 xpath"，而在**知道改动该落在哪个文件**：
改文案跑 `元素定位层`，改环境地址跑 `测试数据层/公共数据.py`。这是维护性，不是生成能力。

## 4. 补强二：调用图 —— 挖出"录制快照里没有的业务知识"

第二遍扫描关键字体，识别它调了哪些本地关键字、内部做了什么：

```
操作日志列表断言(...)
    调用本地关键字: ['操作日志列表加载完成']
    内部行为: ['asserts', 'waits']
IMS操作日志列表断言(...)
    调用本地关键字: 无          ← 对应源码里那行被 # 注释掉了
    内部行为: ['asserts', 'waits']
```

两件事同时被验证：
1. **后定义先引用**能正确处理（`操作日志列表加载完成` 定义在下方，仍被正确关联）。
2. **注释掉的调用不算数**（`IMS` 版本里 `#操作日志列表加载完成` 被跳过）。这是两个版本**真实的行为差异**，不是笔误。

而 `操作日志列表断言` 内部的这段，才是这一节的重点：

```robotframework
${操作时间减少一分钟}=    Date Dec One Min    ${操作时间}
${操作时间增加一分钟}=    Date Add One Min    ${操作时间}
${status}   ${value}=    Run Keyword And Ignore Error    ...    ${操作时间}
${status2}  ${value2}=   Run Keyword And Ignore Error    ...    ${操作时间减少一分钟}
Run Keyword If    '${status}'=='FAIL' and '${status2}'=='FAIL'    ...    ${操作时间增加一分钟}
```

**"操作时间允许 ±1 分钟偏差"** —— 这是业务知识。
它不在 DOM 快照里，不在录制事件里，规则推不出来，模型也猜不到（猜的是一模一样地匹配）。
只要 agent 是"重新写一遍断言"，就必然丢掉这个容错，用例上线即 flaky。
**只有调用 `操作日志列表断言` 才能继承它。**

## 5. 索引给不了的：选哪个变体

`操作日志列表断言` 与 `IMS操作日志列表断言` 的差别只有一处：

```
${来源IP}=${hostIp}      vs      ${来源IP}=${hostIpbj}
```

在 AILink 环境断言 IMS 的日志，用错版本 → IP 永远对不上 → 用例必挂。
索引器能做的极限是**把两个都列出来、把默认值差异摆明**（已做到），
但"这次该用哪个"取决于测试环境，索引不知道，规则也写不出来（除非维护一张环境映射表，而那就是你说的"一直维护规则"）。

结论：这一层必须留给 agent 判断，或者在 plan 阶段向用户确认。

## 6. 对生成路线的三条硬结论

### 6.1 复用的真正价值是"继承坑"，不是省 token

| | agent 手写库调用 | 调用业务关键字 |
|---|---|---|
| 需要精确记忆的符号 | ~10 个（6 个中文长变量名 + 4 个库关键字） | 2 个关键字 + 4 个参数名（签名里直接抄） |
| 写错一个字的后果 | 变量不存在 / 关键字不存在 | 参数名写错会立刻报错，且报错信息明确 |
| 内部等待、重试、±1 分钟容错 | **全部丢失** | 自动继承 |
| 风格一致性 | 每次生成一个样 | 与项目现有用例同构 |

### 6.2 语法层规则 100% 够用，语义层规则 0%

- 解析、闭包、检索、注释识别、调用图 —— 全是确定性代码，16.4ms 跑完，**没有一个字需要 AI**。
- 但"该用普通版还是 IMS 版"、"该断言几条记录"、"操作时间填什么" —— 规则一条都写不出来。

这就是为什么最终形态是**规则做骨架和护栏、AI 做选择**：不是折中，是两件事本来就该分开。

### 6.3 上下文成本可以量化

| 方案 | 体量 | 说明 |
|---|---|---|
| 两份文件全文塞进提示词 | 13,967 字符 ≈ **11,639 token** | 还只是 2 个模块 |
| 全部关键字签名 | 667 字符 ≈ **555 token** | 13 个关键字，够 agent 挑 |
| 命中 1 条的完整实现 | 2,668 字符 ≈ **2,223 token** | 照着风格写 |
| 推荐组合 | 签名全量 + top2 实现 ≈ **5,000 token** | 比全量省 57%，且信息更聚焦 |

上轮外推：1500 个关键字时，签名全量约 1.5 万 token（可行），闭包约 3 千（更优）。

## 7. 仍未覆盖

1. **`*** Test Cases ***` 段只记录用例名**，不解析用例体调了哪些关键字 —— 所以"从用例推闭包"只能沿 `Resource` 走，不能按实际调用裁剪。
2. **`.py` 变量文件全量读取**。这次只有 4 个变量；真实项目里可能有几百 KB，需要做惰性/按需解析。
3. **变体消歧没有机制**，只能靠 agent 判断或人工确认（第 5 节）。
4. 元素定位层用的是我造的替身，**真实项目的变量命名规律、重复率、坏引用率未知**。
5. `[Documentation]` 在这两份文件里完全缺失，只靠行内 `#` 注释 —— 检索得分的注释权重（1.2）在真实项目上可能偏低。

## 8. 一句话结论

**这两份文件证明了：索引器能把「项目里有哪些可复用的关键字、它们的参数和内部行为」在 16ms 内准确提取出来（13/13、7/7、100%），
而生成侧必须调用这些关键字而不是重写 —— 因为重写会丢掉「操作时间 ±1 分钟」这类录制快照里根本不存在的业务知识。**

留给 AI 的恰好是索引算不出来的那部分：选哪个变体、断言几条、参数填什么。
