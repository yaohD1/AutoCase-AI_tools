# RF 关键字索引器验证报告

> 目的：验证「不把 2GB 项目塞进上下文」的前提下，能否让模型准确知道项目里有哪些可复用关键字。
> 结论：**可行**。解析零依赖、6ms 扫完、检索能命中注释级语义。但有 4 个明确局限，见第 5 节。
>
> **后续**：本报告基于虚构样本。真实项目文件（`操作日志.resource` / `安全日志.resource`）的验证见
> [`rf_keyword_index_real_validation.md`](./rf_keyword_index_real_validation.md) —— 那里补上了变量溯源与调用图，
> 并给出了「为什么必须复用业务关键字而不能重写」的实证。

---

## 1. 验证方式

手工构造一个与真实项目同构的样本（不是真实项目，避免依赖内网）：

```
.probe/rf_index/
  indexer.py          解析器 + 引用闭包 + 检索（约 230 行，纯标准库）
  demo.py             验证脚本
  data/               8 个文件 / 33 个关键字 / 2 层 Resource 引用
    登录/公共的前置后置.resource
    页面对象层/页面公共关键字.resource
    页面对象层/左侧菜单页面操作.resource
    页面对象层/日常运维/网元列表/网元列表页面操作.resource
    页面对象层/日常运维/日志管理/安全日志页面操作.resource
    页面对象层/其他模块/告警管理页面操作.resource      ← 无关模块，用于验证闭包过滤
    测试用例/网元列表/网元列表.robot
    测试用例/其他/告警查询.robot                        ← 无关用例
```

样本刻意保留真实写法：中文关键字名、中文参数、`[Arguments]` 多行 `...` 续行、默认值 `${网元版本}=test`、关键字上方注释块、`[Documentation]`、相对路径含 `../`。

## 3. 引用闭包

从 `测试用例/网元列表/网元列表.robot` 出发，深度 2：

```
闭包 6 个文件（全项目 8 个），关键字 30 / 33
```

样本太小，所以比例高（88%）。真实项目里无关模块通常占 90%+，闭包收益会显著得多。

机制本身成立：**从用例出发顺着 `Resource` 走，不需要扫描、不需要猜**。

## 5. token 估算

实测（8 文件 / 33 关键字）：

| 形态 | 字符 | ≈ token |
|---|---|---|
| a. 全项目原文 | 7,568 | 6,309 |
| b. 全项目签名索引 | 1,750 | 1,458 |
| c. 闭包原文（深度2） | 6,624 | 5,520 |
| d. 闭包签名索引 | 1,597 | 1,330 |
| e. 检索命中 5 条（签名+文档） | 403 | 335 |

按当前密度线性外推到真实规模（500 文件 / 1500 关键字）：

| 形态 | ≈ token | 可用性 |
|---|---|---|
| 全项目原文 | 28 万+ | **不可行** |
| 全项目签名索引 | 6~8 万 | 勉强，偏贵 |
| 闭包签名索引（按 20% 估） | 1.3~1.6 万 | **舒适** |
| 检索 top 20 | 0.2~0.3 万 | **最省** |

结论：**闭包 + 检索是必需的，不是优化项。**

## 6. 优点

1. **快且可缓存**：8 文件 6.4ms，线性外推 500 文件约 400ms；按 mtime 增量更新后，日常生成只读缓存。
2. **零依赖**：纯标准库，不引入 RF 运行时、不需要 `robot` 命令。
3. **参数完整**：默认值、多行续行、中文参数名都保留，模型不会传错参数名。
4. **能发现项目问题**：坏引用、缺失文件当场报出来（实测抓到一次）。
5. **注释参与检索**：`验证码识别 → 拖动完成拼图` 证明「语义线索藏在注释里」这条路成立。
6. **闭包天然抗干扰**：无关模块根本进不了候选集，比"全量塞进去 + 让模型自己筛"可靠。
7. **可单测**：纯函数，输入文件输出结构，golden 测试很好写。

## 7. 缺点与局限（必须正视）

| # | 局限 | 影响 | 缓解 |
|---|---|---|---|
| 1 | **字面匹配，不懂同义词** | 「登陆」搜不到「登录」、「重启」搜不到「复位」 | 加同义词表/拼音首字母；或让模型用不同措辞多查两次 |
| 2 | **不知道关键字「做什么」** | 只有签名 + 注释。**注释为空的项检索质量会明显下降** | 无解，只能靠名字；或对高频关键字人工补注释 |
| 3 | 不解析 `*** Variables ***` 常量 | `${DEFAULT_TIMEOUT}` 只是字符串，不知道实际值 | 对生成影响小（不需要值） |
| 4 | 同名关键字冲突未检测 | 两个文件定义同名关键字时，模型可能选错来源 | 加冲突检测，冲突时全部列出让模型选 |
| 5 | 闭包深度固定 2 | 深层嵌套（3~4 层）会漏 | 改成"不设深度但设上限（如 30 文件）" |
| 6 | 只覆盖常规 RF 写法 | `[Template]` 数据驱动、`FOR` 循环内调用未建模 | 当前场景用不到，遇到再加 |
| 7 | 索引会过期 | 文件改了不重建，模型看到旧签名 | mtime 校验 + 启动时重建 |
| 8 | **只解决「有什么」，不解决「用哪个」** | 候选集给全了，选哪个仍靠模型 | 这是设计意图，不是缺陷；但意味着**索引替代不了模型判断** |

第 2 条最值得警惕：**这套方案的召回质量，直接取决于项目注释的规范程度。** 你给的这份 RF 注释写得很好，所以效果看起来好；如果真实项目里大量关键字没有注释，检索会退化成"只能按名字搜"。

第 8 条决定了它的定位：**它是检索层，不是决策层。** 它把"读 2GB"变成"读 2 万 token"，但"这 8 步该用哪 5 个关键字"仍然要模型判断。

---

## 8. 结论

**适用**：

- 中大型 RF 项目（关键字 > 100 个），否则直接全读更省事
- 注释有一定规范度（至少关键字名可读）
- 需要反复生成（索引可复用，边际成本趋近于零）

**不适用**：

- 小项目（< 50 个关键字）：全读就行，加索引是过度设计
- 注释几乎为空且命名随意的项目：检索召回会很差
- 关键字高度动态生成的项目（RF 里少见）

**产品化还差什么**：

1. 增量更新（mtime → 只重解析变化的文件）
2. 同名冲突检测
3. `search()` 与 IR 特征提取对接：IR 里有菜单名、元素文本、URL，直接喂进检索
4. 与 plan 阶段联动：候选集 → 模型选 → 输出「复用哪些 / 缺哪些」

**代码量估计**：当前原型 230 行，产品化补齐上述 4 项约 350 行 + 测试 150 行。
