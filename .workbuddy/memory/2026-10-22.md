# 2026-10-22

## 录制侧新增「刷新页面」步骤（reload）

背景：此前刷新完全录不到，原因两处——`_handle_navigated` 里「URL 没变就 return」把刷新直接吞掉；
以及「上一步是 click 就不记导航」会永久生效（点完按钮再刷新也丢）。

改动：
- `ir.STEP_TYPES` 加 `reload`；HF/回放/生成链路全部覆盖 `reload`。
- `session.py`：
  - 新增 `NAV_TYPE_JS`，用 `performance.getEntriesByType('navigation')[0].type`
    区分 navigate / reload / back_forward，不再靠 URL 变没变猜起因。
  - 点击抑制从「上一步是 click」改成 `_pending_click`（frame id → 时间戳，1.5s 窗口，一次性）。
    点击引起的跳转不记 goto；刷新永远记（判断顺序：reload 分支在 click 消费之前）。
  - `add_reload_step` / `_add_reload` / `_reload_page`：插步骤并按需真的刷新
    （嵌入模式刷 iframe，非嵌入 `page.reload`），用 `_manual_reload_at`(3s) 吞掉自动检测到的那一条。
  - `_insert_step` 抽出来公用，顺手修了「锚点本身是末尾 new_page 时 IndexError」。
  - `_handle_new_page` / `_handle_navigated` 加「只在 recording 状态入库」的守卫
    （停止后浏览器还开着，否则新标签页/导航还会往列表里塞步骤）。
- emit 提示词 + `.opencode/prompts/recording-emitter.md`（真正生效的系统提示词，两份都要改）：
  RF → `Reload Page`，PW → `page.reload()`，明确禁止写成 Go To / goto(page.url())。
- 前端：工具栏「刷新页面」按钮、行内「+」加「插入刷新页面」、
  STEP_LABELS/描述、回放明细显示中文类型与「刷新当前页面」。

测试：新增 `test_recording_navigation.py`（7 条真浏览器：刷新可录、点完再刷也在、
点击不额外记 goto、手工按钮只记一条且真刷新、停止后不录但可插、插入位置）。
路由/回放/emit/规则用例各补 1~5 条。后端 109（无浏览器）+ 4 组真浏览器全绿，前端 build 通过。

## 修复：刷新被记成多条 / 记成「打开网址」

用户在真实 SPA 上点一次「刷新页面」出现 3 条刷新步骤，手动 F5 也异常。实测复现：
Vue Router 启动时用 replaceState 做 same-document 导航，Playwright 对每次都会再发一个
`framenavigated`，而 `performance.getEntriesByType('navigation')[0].type` 始终是首次加载
那条（刷新的三条都读成 reload）——于是把「导航事件次数」当成了「用户意图的导航次数」。

修法（`session.py`）：
- `NAV_INFO_JS` 同时返回 `{type, origin}`，`origin` 即 `performance.timeOrigin`，是 document
  身份证。同一 document 的再次上报 timeOrigin 相同 → 去重（`_doc_stamp`）。
- 读到 timeOrigin 与上次相同、且疑似导航刚提交时，等 80ms 再读一次（evaluate 可能还落在旧
  document 上），避免把真刷新整次吞掉。
- 新标签页首跳用 `_skip_nav` 显式吞掉，避免「新 document + 地址没变」被兜底逻辑判成刷新。
- 兜底：换了 document、地址没变、起因读不到 → 记 reload（原来是记 goto）。
- `MANUAL_RELOAD_SECONDS` 3 → 5 秒。

真实原因排查中发现一个坑：同名方法 `_nav_info` 被定义了两次，后一个覆盖前一个，导致所有
导航调用抛 TypeError 并被 `_process_inbox` 静默吞掉（`_errors` 里才对得上）。`_process_inbox`
吞异常没有任何上报，后续若要排障需要把 `_errors` 暴露到 snapshot。

测试：`test_recording_navigation.py` 新增 `SpaNavigationTest`（3 条，真浏览器，页面用
replaceState 造多次上报），断言「多次事件只产生一条步骤」。后端 109（无浏览器）+
42（真浏览器）全绿。

## 决定：刷新取消自动检测，只保留工具栏按钮

用户判断自动检测 bug 偏多，要求收敛（2026-10-22）。实现：
- `_handle_navigated` 里 `nav_type == 'reload'` 直接 return（不记步骤）；
- 地址没变却换了 document 也 return（不记成「打开页面」）；
- 换地址的跳转、前进后退仍记 goto，点击引起的跳转仍不记；
- 删掉 `MANUAL_RELOAD_SECONDS` 与 `_manual_reload_at`（不再需要「吞掉自己刷的那次」窗口）；
- 保留 `_doc_stamp`（timeOrigin 去重）与 `_skip_nav`（新标签页首跳），它们防的是 SPA 重复上报。

「刷新页面」按钮仍是唯一入口：插入一步 + 真的刷新浏览器（保证后续步骤落在刷新后的页面上），
行内「+」可插到任意一步之后。前端 tooltip 明确「按 F5 不会被录制」。

测试反转：`test_reload_is_not_recorded_automatically`、`test_reload_after_a_click_is_not_recorded_either`、
`SpaNavigationTest.test_one_reload_is_recorded_once`（断言刷新不产生步骤，但事件确实多条）。
导航组 10 条真浏览器用例、109 无浏览器、32 其余真浏览器全绿，前端 build 通过。

## 新增：轮询等待（不做通用循环）

用户提出真实场景：设备重启后要测重启时间，点重启 → 每 5 秒刷新一次 → 每次判断判定元素是否出现，最多 360 秒。
讨论结论：这不属于「循环」，是**轮询等待（polling / wait-until）**，和「数据遍历 / 固定重复」是两回事。
通用循环不做（要打破扁平 IR、改 remove/move/insert/renumber 四处索引，只换来「连点 N 次」的低频需求）；
轮询等待做（复用已有 `wait` 步骤，只加三个参数，两个框架都有原生语法兜底）。

实现：
- `ir.POLL_INTENT_TYPES = ('wait_visible', 'wait_hidden')`，`STEP_TYPES` 不变（仍是 wait）。
- `intent.py`：intent 增加 `timeout` / `interval` / `reload`；`_poll_fields()` 校验
  （timeout 1~3600、interval 1~300、interval ≤ timeout；**勾了 reload 必须给 timeout**，
  否则「每 5 秒刷一次却只等默认 5 秒」等于没等）。其他意图类型强制这三个字段为空。
- `replay.py`：`_assert` 拆成 `_assert_once` + 分两路口径——不刷新走 Playwright 原生等待
  （timeout 直接生效），刷新走 `_poll_with_reload` 手工循环（单次判断 1s，失败即 reload + 等 interval）。
  `_run_step` 改为返回 `(chosen, poll_meta)`，回放明细带「轮询 Ns / 刷新 M 次」。
  超时报错文案是「轮询等待 X 秒仍未成立」，不能报成「元素不存在」——否则用户会去改定位，
  而实际问题在系统没起来。
- `verify.py`：`check()` 包一层 `_check()`，轮询等待的「此刻不成立」附 `poll` 字段，
  前端换中性色 + 换提示语（轮询的此刻几乎必然不成立，红色是错误信号）。
- 生成侧两处都要改：`emit.FRAMEWORK_RULES` 与 `.opencode/prompts/recording-emitter.md`
  （后者才是真正生效的系统提示词，历史上漏改过一次）。
  PW 用 `expect.poll(async () => { await page.reload(); return loc.isVisible(); }, {timeout, intervals})`，
  回调里**不能**再套 `toBeVisible`（它自己会等，会把间隔吃掉）。
  RF 用 `Wait Until Keyword Succeeds <timeout>s <interval>s Reload And Check`，
  keyword 内层超时必须**严格小于 interval**，否则单次判断吃满整个节奏。
- 前端：`wait_visible/wait_hidden` 展开「最长等 N 秒 / 等不到就刷新页面 / 每 N 秒刷一次」，
  默认 30 秒 + 不刷新（刷新会冲掉表单、登录态）；步骤描述拼成「最多 360 秒，每 5 秒刷新一次」。
  按钮文案改为「添加等待 / 轮询」。

测试：新增 `test_recording_poll.py` 17 条（9 条字段校验 + 5 条真浏览器 + 2 条提示词 + 1 条旧行为）。
其中反向用例 `test_wait_without_timeout_fails_on_slow_page` 用 6 秒才渲染的页面证明 timeout 真生效，
不是「碰巧默认值就够」。回归：86（核心）+ 34（路由/工具链）+ 25（导航/回放/验证）全绿，前端 build 通过。
另写了 `.tmp-spike/ui_poll_check.py` 做界面冒烟（mock 掉后端，9 项通过）：
注意 route 正则必须写 `^http://localhost:PORT/api/`，写成 `.*/api/.*` 会把 `/src/api/index.js`
这个前端模块也拦掉，页面直接空白。

## 结论：定位主路径不上 AI（讨论后定调）

实测数据（`.tmp-spike/_cost_probe.py`、`_cost_probe2.py`）：
- 300 行 × 4 列的设备列表页：75KB HTML / 2446 节点 / 626 个可交互元素 ≈ 23k token；
  真实后台页普遍 300KB–1.5MB → 100k–450k token，很多模型上下文装不下。
- 现方案每步 7 条候选各 count 一次：2–22ms（命中 300 条 xpath 最慢），整步 <100ms。
- 取整页 outerHTML 只要 6ms——瓶颈从来不是取 DOM，是模型。
- 结论：全 DOM 喂模型每步 2–5s、30 步要多等 1–2.5 分钟，成本 ¥0.6–12/用例，定位提升估 5–15%，
  且模型给不出「这条定位确实唯一」的保证，仍要 count 验证。**不值。**
- 真正该补的是规则候选：列表行内元素按「行文本锚定」（//tr[td[1]='设备-5']//button[.='删除']），
  可纯规则做，覆盖列表场景，收益高于 AI。
- 顺带提过「行锚定候选」（tr/li 行文本 + 行内按钮，`//tr[td[1]='设备-5']//button[.='删除']`），
  位置在 locators.py build_specs + recorder.js snap 加 row_tag/row_text；用户评估后决定**也不做**，
  不要再重复提议。定位逻辑到此冻结，除非出现真实的回放失败案例。
- 如果上 AI，唯一合理位置：① 回放失败后的自愈 ② 停止录制后一次性批量救降级步骤；
  输入给裁剪上下文（目标元素 + 3 层祖先 + 同级可交互元素 + 候选清单，1–3k token），
  输出候选后仍走 count() 裁决 —— 「AI 提议、规则裁决」。

## 按键（press）与弹窗（dialog）已补

- IR 加两种步骤类型。press 的 value 存键名（Playwright 写法 Enter / Control+Enter），
  dialog 另存 `{kind, message, action}`，value 同存一遍 action 便于前端读。
- recorder.js：只录有语义的键（Enter/Escape/Tab/BackSpace/Delete/方向键/Home/End/PageUp/PageDown/Space），
  纯文字输入不录（fill 已覆盖），修饰键单独按下不录。Alt+拾取时 keydown 直接跳过。
- **两类「键盘合成 click」必须靠 detail===0 区分**：
  焦点在按钮上按 Enter（要的就是这次点击 → 记 click、不记 press）；
  输入框按 Enter 提交表单（浏览器给提交按钮补一次 click → 记 press、不记 click）。
  只看 detail 会两边都丢或两边都记，必须配合 `lastKeyOnClickable`。
- dialog：`page.on('dialog')` 回调里**必须立刻 accept**，Playwright 有监听后不再自动接管，
  不处理页面会挂起（用户看到「点了就卡死」）。代价是问不到用户点的是确定还是取消，
  录到的固定是 accept，需要取消时在步骤上改（dialogs 已进 EDITABLE_FIELDS）。
  beforeunload 不记步骤。
- **发现并修掉一个真 bug**：会跳转的步骤（点链接、回车提交）在 inbox 处理时页面已经翻篇，
  所有候选 count 都是 0 → primary=None → `best_effort` 返回 None → 生成被整体拒绝。
  现在 `vanished_primary()` 兜底：全 0 时用快照语义最强的那条顶上，count 记 0、target 打
  `unverified`，前端徽标显示「未核实」；`_revalidate_all` 对 unverified 的目标保留 primary；
  `emit._locator_info` 只对 unverified 放行（真正失效的仍然拦）。
- 回放：press → `loc.press()`；dialog 必须在**触发它的那一步之前**注册 handler（`page.once`），
  等走到 dialog 步骤再注册已经晚了，`_run` 里用 probe 提前一步 arm，dialog 步骤只检查有没有真的弹，
  没弹就报错而不是装作走通。撤销上一步时 dialog 和它前面的 click 一起删（同 new_page）。
- 生成提示词两处都改了（emit.py + .opencode/prompts/recording-emitter.md），
  PW 的 dialog 提前注册这一条是最容易写错的地方。

## 断言与等待合并成一个入口（2026-10-22 晚）

- **前提认知**：assert 与 wait 在 IR 里本来就是同一个东西——`replay._assert_once` 里
  `visible` 和 `wait_visible` 走同一个分支，差别只有 timeout；`step_type_for_intent` 区分两者
  只是为了生成端挑模板。所以「添加等待 / 轮询」按钮是重复入口，去掉。
- 工具栏从 7 个按钮变 6 个：开始 / 拾取元素 / 关闭浏览器 | 刷新页面 / 添加断言 / 固定等待。
  行内「+」菜单同步去掉「插入等待 / 轮询」。
- 断言卡里加**折叠高级区**（`.advanced-box`）：默认收起=立即判定，展开勾「允许等待」+「期间刷新」。
  选折叠而不是下拉框，是因为收起态能显示摘要（`立即判定` / `最多 360 秒 · 每 5 秒刷新`），
  下拉框收起时看不出是不是在等待。问号 tooltip 用 `placement="top-end"`，`top` 会超出右边界被裁。
- **三角箭头不能用 `▸` 字符**：11px 下中文字体把它渲染成一个点，改 CSS 边框三角 + rotate。
- 后端判据改成「有没有 timeout」：
  - `ir.step_type_for_intent(kind, intent=None)`：intent 带 timeout → wait，否则 assert；
    `wait_visible/wait_hidden` 仍映射 wait（读旧数据）。
  - `intent.validate`：除 sleep 外所有类型都能带 timeout/interval/reload（原来只 wait_* 能）。
  - 新增 `ir.CONDITION_INTENT_TYPES`（8 种）供提示词用，`INTENT_TYPES` 保留 wait_* 做兼容。
  - 新增 `intent.apply_poll(intent, changes)` 供就地改，校验复用 `_poll_fields`，不另起一套规则。
- **就地编辑**：`EDITABLE_FIELDS` 加 `assert` / `wait` → `('timeout','interval','reload')`；
  `update_step` 改完重算 `step['type']`，所以 30 秒 → 立即断言 → 再改回 60 秒可以来回切。
  `timeout: null` 表示退回立即断言。`_mutate` 把 RecordingError 转 409（不是 400）。
- 前端 `draft.allowWait` 是唯一开关，`buildFormIntent` 只在勾了才写 timeout。
  `applyParsed` 把 `wait_visible/wait_hidden` 用 `LEGACY_WAIT` 拆成 `visible/hidden + allowWait`，
  解析出等待时自动展开高级区。
- 步骤行标识：`wait` 的 kind tag 带 `Timer` 小图标（`assert` 不带），描述尾部带「最多 N 秒，每 M 秒刷新一次」，
  一眼能分出「会等的」和「立即判定」。
- 生成提示词从只覆盖 visible/hidden 扩到 8 种条件（emit.py 与 md 两份都改）：
  RF 不刷新时用原生带超时关键字（Wait Until Element Contains / Page Contains / Location Contains），
  text_equals/value_equals/enabled 用 `Wait Until Keyword Succeeds` 包 Should；
  PW 刷新时 `expect.poll` 回调里必须写即时判断，不能套 matcher（matcher 自己会等，吃掉 interval）。
  `emit._steps_for_prompt` 把「assert + timeout」归一成 type=wait，旧数据也不会走错模板。
- 测试：`test_recording_poll` 21 项（含 `test_any_condition_can_carry_timeout`、`test_apply_poll_back_and_forth`）、
  routes 新增 2 项（插入即 wait / 改回 assert、只勾刷新无 timeout 要拦）。非浏览器 107 项全绿。

## 修复：文本框里退格改字被录成 press + 多条 fill

- 现象：账号框输错一个字符按退格，每按一次生成「按键 Backspace」+ 一条新 fill，一次输入被切成多步。
- 根因：keydown 把所有 RECORD_KEYS 都 emit 成 press，而 fill 合并要求「上一条也是 fill」，press 夹在中间就断了合并。
