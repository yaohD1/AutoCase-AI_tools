
## 断言解析：录制期常驻 opencode 进程（解析提速）

- 实测病因：一次解析 6.5–8.1s，其中「进程首次模型调用」占 5–7s（provider 建连 + opencode 初始化），起进程只占 1.0s；同进程第二次起只要 1.4–4s。
- 方案：录制开始就起一个 opencode serve 并在后台预热一次，停止后延迟 90 秒杀。
  - 新增 `backend/app/services/recording/ask_pool.py`（AskPool）：状态机 starting/warming/ready/failed/stopped、`ask()`、`note_model()`（换模型补预热）、`fail()`、延迟 stop 用 daemon Timer、atexit 兜底、stderr 管道关闭。
  - `session.py`：`start_new(ask_daemon/ask_model/ask_config)`；`_run` 里 status=recording 后 `_start_ask_pool()`（只起线程不阻塞）；stop 命令延迟杀；`_shutdown`/`_run finally` 立即杀；snapshot 增加 `ask` 字段。
  - `routes/recording.py`：`_ask_text()` 优先走常驻池，不可用退回一次性 `ask_text`；失败后 `pool.fail()` 不再反复等。
  - 前端 `Recording.vue`：工具栏下一行 `.ask-hint`（绿点就绪 / 黄点启动中 / 红点不可用，title 给原因，off 时整行不显示）。
- 附带修复：模型返回 `timeout: 0` 视为「不等待」而不是报「最长等待需在 0 到 3600 秒之间」。
- 实测（volcengine-plan/deepseek-v4-flash）：就绪 6.8–8.1s（首次冷启动 19.5s）；解析 2.5–3.4s（原 6.5–8.1s）。内存代价：opencode serve 常驻 549MB(`--pure`)/666–688MB。
- 测试：新增 test_recording_ask_pool.py 10 条；路由测试用 RECORDING_ASK_DAEMON=0 关掉真进程；浏览器用例统一传 ask_daemon=False。回归：146(非浏览器)+62(浏览器)+22(轮询) 全绿；前端 build 通过；UI 冒烟 5 项通过。

## 修复：一次输入被拆成多条「输入」（元素身份用了 CSS 路径）

- 现象：密码框慢慢输，录成「输入 1 / 输入 12345678 / 输入 123456789」，目标都是同一个 getByLabel('密码') 且唯一。
- 排除：不是轮询导致。pump 是 150ms（PUMP_MS），事件 FIFO 入队按序处理，合并规则没有时间窗；实测同一框内停 200ms/1.2s/2.5s 仍然并成一条。
- 根因：`session.py _handle_event` 里 `key = (snap['css'], id(frame))` 用 CSS 路径当元素身份。真实页面在第一次输入后会改 DOM（包一层 el-input、插隐藏 input、冒校验错误态），cssPath 多一级 → key 变 → 合并断掉。已用两种结构变形稳定复现。
- 修复：新增 `RecordingSession._merge_key(snap, primary, frame)` —— 主定位唯一时用 `('locator', primary['desc'], id(frame))`（选择器即身份，DOM 重排不影响），没有唯一候选才退回结构路径。`key = self._merge_key(...)`。别名仍走 `_alias_key`（语义不同：别名要跨步骤唯一）。
- 注意：`_press_only_edits_text` 的 press pop 也用这个 key，退格改字同样受益。
- 测试：test_recording_press_dialog.py 新增 DomShiftMergeTest(3)：wrap/hidden 两种结构变形都只剩一条 fill；两个不同输入框不合并（防过度合并）。反向验证：去掉修复这 3 条全红。
- 回归：146(非浏览器) + 39(回放/导航/轮询) + 27(按键/输入) 全绿。
- 探针：.tmp-spike/probe_dom_shift.py（结构变形复现）、repro_slow_typing.py（停顿不拆分）、probe_split_cause.py（iframe/重渲染）。

## 生成范围检查重做：权限预防 + git 检测，不再快照还原

- 起因：生成报 500，根因是 `guard.snapshot()` 对 555MB 工作区（554MB 全是 reports/ midscene_run/ test-results/ 产物）抛 GuardError，且抛在 try 外面 → HTML 500 吞掉原因。
- 结论：快照=事后取证，用错了层级。改成三层：
  1. **预防**：`OpenCodeRunner._emit_config()` 每次生成写一份临时 opencode 配置，把 recording-emitter 的 `edit`/`write` 锁成 `{"*":"deny", 目标: "allow"}`，`bash`/`task` deny。临时配置必须与原配置**同目录**（`{file:...}` 提示词按配置文件目录解析）。
  2. **检测**：`guard.py` 重写。git 模式（工作区=仓库顶层且有 commit）= `git stash create` 打临时 commit + `git diff --name-only`，未跟踪文件另记 (size,mtime) 指纹；非 git 退回纯 stat 指纹。产物目录 + 工作区 `.gitignore` 顶层目录名一律排除。实测 555MB 工作区：snapshot 0.3s、changed 0.1s（原来直接失败）。
  3. **修复**：**只报告不还原**。越界写进结果 `outside` 字段，前端列出清单 + git checkout 提示；失败时只删「本次产出且原本不存在」的目标文件，原本存在的保留并提示 git 恢复。
- **踩到的坑**：opencode 权限 pattern 是拿**绝对路径**匹配的，写 `allowed.txt` 永远不命中（会静默全 deny）。必须用 `**/相对路径` 或绝对路径；代码里三种形式都写。`edit` 权限覆盖 edit/write/apply_patch；`*: deny` 必须排第一（最后命中者生效）。
- 其他改动：`__init__.py` 加全局异常处理（/api 一律回 JSON，否则前端只能看到 status code 500）；`target_ok` 禁 `* ? [ ]`（会放大 glob 权限）；emitter 提示词明确「只目标文件可写，被拒不要重试」。
- 测试：新增 `test_recording_guard.py` 14 条（git/指纹/产物排除/.gitignore/权限配置）；`test_recording_emit.py` 两个用例改为「不回滚」语义。回归 160（非浏览器）+ 66（浏览器）全绿；前端 build 通过。
- 实测：emitter 能写目标文件、写 other.txt 被拒；真实 555MB 工作区跑完整 generate，changed 只有目标文件。
