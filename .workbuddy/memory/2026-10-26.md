
## 录制：定位预览（框选 + 人眼确认 + 指定第几个）

- 起因：不唯一时步骤栏只有一个「不唯一」标签，用户不知道是哪几个、怎么判断。讨论后否掉了「父容器锚定」（环境该在跑之前固定，锚定等于替环境兜底），改做「所见即所得」。
- 关键实测：两个都叫「确定」的按钮，text/行文本/y 坐标**完全相同**，只有 x 不同 → 文字摘要在这种场景下信息量为 0，只有画面能分辨。
- 实现：
  - `overlay.js`（新文件，`session._read_js` 读取）：用 `evaluate_all` 把匹配元素全部框出+编号，页面坐标（rect+scrollX/Y），**先 scrollIntoView 再算坐标**（反过来整体偏移一个滚动距离；实测滚动 300px 后 dx=dy=0）。选中实心红 `#ff3b30`，其余灰虚线。
  - `session.py`：`MATCH_SUMMARY_JS`（录制时存 `target.matches`：tag/text/row/visible，最多 10 条）、`_collect_matches`（只在 count>1 的候选里取最窄那条）、`highlight/clear_highlight/set_chosen` 三个命令 + `_drain_commands` 分支、`_overlay_frame`。
  - 采集条件不只 ambiguous：`getByRole` 命中多个时主定位会退到 css 绝对路径（`fragile`），这种步骤同样要存 matches——否则用户看不到「其实有 3 个」。
  - `_highlight_now` 选候选优先级：用户选的 → matches.desc（能框出全部，信息量最大）→ pick_for → best_effort。
  - `_revalidate_all`：越界标 `index_invalid`，**不静默改回第一个**（会点到别的元素）。
  - `emit._locator_info` 新增 `mode='chosen'`：`target.chosen` 优先，且要求该候选在目标框架池里、count>1。`_match_texts` 把 matches 压成 `{of, each}` 进提示词，模型据此在 nth 那行写注释。
  - 路由：`POST /recording/highlight`、`/highlight/clear`、`/steps/<no>/chosen`（desc 必传）。
  - 前端：步骤行准星 `.peek-btn` + `.peek-panel` 候选条（选哪个哪个变红并落库）、`withNth` 显示 `.nth(n)`（RF 用中文「第 N 个」）、新增状态 `chosen`（已选定，绿）/`invalid`（序号失效，红）。`blockers` 纳入 invalid，文案从「不唯一」改「待确认」。
- 测试：`test_recording_highlight.py` 24 条（narrowest / 摘要采集 / fragile 也存 / 画框与重画 / 选中态 / 越界回退 / chosen 落库与停止保留 / 越界失效 / emit 优先 chosen / 提示词带 matches）；`test_recording_routes.py` +4 条接口契约。
- 回归：188(非浏览器) + 66(浏览器) 全绿；前端 build 通过；UI 冒烟 `.tmp-spike/ui_peek.py` 14 项全过，截图 `shots/peek-panel.png`。

## 录制两个 bug 排查（只诊断，未改代码）

- **目标文件丢失**：录制窗口是 `chromium.launch()` + `new_context()` 的全新 profile，localStorage 为空。`startRecording` 只发 model/workspace/framework，后端 `_prefill` 也只回填这 3 项，`target_path`/`title`/`python` 从未传到录制窗口。所以开始页填的目标文件在录制窗口里是空的，生成卡提示「还没有填写目标文件」。每次新录制都会丢，手填只对当次窗口有效。
- **停止后登录步骤全变「不唯一」**：不是快照坏。本次会话 `snap.frame_url`：步骤 2–6 是 `/login`，步骤 7–8 是 `/global`；停止时页面已在 `/global`。`_mark_stopped(revalidate=True)` → `_revalidate_all()` 把所有 target 拿**当前 document** 重新 count：登录页元素全 0 → `rank()` 无 primary → `status='ambiguous'`；前端 `pickFor` 找不到 count==1，就显示「不唯一」。
- 关键证据：步骤 3/4/5/6 所有候选 count=0（连 css/rf_id 都是 0），步骤 7/8 placeholder count=1。`snap` 本身仍保留 `id=password-login_username`、`label/placeholder`，说明快照没坏，是停止时把 `candidates` 的 count 用错误页面覆盖了。
- 更严重：`emit._locator_info` 对 3/4/5/6 返回 None（全 0 且没有 `unverified`）→ 生成会被拦下报「第 3、4、5、6 步的目标元素在页面上已经找不到」。只修目标文件后就会暴露这个问题。
- 根因：`unverified` 只在录制当场 count 0 时设置（1529–1535），「录制时唯一、之后页面翻走」的步骤没有这个标记。停止重校验缺少「录制时 document == 当前 document」的判断。
- 修法方向：start 传 target_path/title/python 并由 `_prefill` 回填；停止重校验按录制时 document（frame_url 或 timeOrigin）过滤，已翻页的保留录制时候选/状态并标「未核实/页面已翻页」，不覆盖成 0，生成端按录制时定位放行。

## 生成体验三项改造（用户确认「都按推荐方案」）

- **入口统一（方案 B）**：主界面 `/recording` 和面板 `?panel=1` 都会显示生成卡，之前各自 `generating` 本地状态，点完另一边还能点。现在状态放服务端：`services/recording/progress.py` 的 `PROGRESS`（模块级单例，带锁）随 `snapshot()` 的 `emit` 字段返回；`PROGRESS.start()` 只有一个能成功，后到请求 409，前端看到 409 不报错、跟着进度走。
- **进度条**：`emit.generate(..., progress=回调)` 打点 prepare→detect→snapshot→writing→check→validate（可退回 repair）→record→done；百分比只给基准值 + cap，前端按 `stage_at` 指数插值（250ms tick）。`progress.finish(result)` 只保留展示字段（剔 `reply`），`fail()` 记 message/details；`conflict` 走 `reset()` 而不是 fail。
- **停止后轮询**：原来 `watch(status)` 一停就 `stopPolling()`，生成进度永远刷不到。改成 `syncPolling()`：recording/starting 或生成中 1s，其余 2s，`pollEnabled` 只在 keep-alive onDeactivated 关。**这是本次最容易漏的一处**。
- **权限根因（实证）**：opencode 1.19 `edit` 权限调用 `ask({permission:"edit", patterns:[path.relative(worktree, filepath)]})`——匹配**相对工作区路径**。之前白名单写 `**/rel` + 绝对路径，根目录文件一条都不中，只剩 `*: deny` → 「agent 没写出目标文件」。修法：`rule` 第一条 allow 直接是 `rel`（外加 `./rel`、`**/rel`、绝对路径兜底）。`opencode debug agent <name>` 可验证规则被解析，但**它会叠加项目根 opencode.json**（`*: deny` 会被覆盖成 allow），别拿它判断最终 deny 是否生效。
- 测试：新增 `test_recording_progress.py`（11 个状态机 + 5 个权限规则），`test_recording_generate_route.py` +3（409 互斥 / 失败落进度 / 冲突 reset），`test_recording_records.py` 的 fake_generate 加 `progress` 参数。回归 204 全绿；前端 build 通过。
- 已重启后端（旧进程是 Python39 直跑但没装 flask，实际要用 `.venv/Scripts/python.exe backend/run.py`）。**重启清掉了用户的录制会话**（10 步），需重录。

## 排查：生成「token 没咋消耗 + 600s 超时」

- 现象：midscene-ui-test 生成 test-corekg.spec.ts，进度停在「第 1 轮修正校验错误」，600s 超时，模型侧 token 很少。
- 实证（opencode.db 的 session/message 表）：first 会话 196s（4 轮，in 14444 / out 888 / reasoning 10763）；repair 会话 600s（6 轮全在读文件，in 19789 / out 655 / reasoning 33660），最后一轮 273s 只产出 125 个输出 token（约 60 tok/s 思考），随后被 timeout 中止。`session.cost` 记 0：volcengine-plan 这个 provider 没配 cost 表。
- **根因**：`toolchain.tsc_check(workspace)` 跑的是整项目 `tsc --noEmit`，工作区里有个**未被 git 跟踪的模板文件** `src/fixtures/seed.spec.ts`（Playwright seed 模板，`expect`/`page` 未使用），在 `noUnusedLocals/noUnusedParameters` 下报 2 个 TS6133。生成的目标文件本身零错误，却被基线错误判成校验失败。
- 次因：repair 是**新开一个 session**，只给一句「上一次写入的 X 校验失败」+ 指向别的文件的报错，agent 没有上下文，全程在核对矛盾、读了 8 个文件，600s 一次都没写。`MAX_REPAIR_ROUNDS=1`，超时后 `_abort` 把已写好的目标文件删了（内容可从 opencode.db 的 write part 取回）。
- 结论：这个工作区**每次生成都会失败**，不是偶发。修法方向：tsc 输出按 target_path 过滤（或在提示里区分基线错误）、repair 复用同 session、失败别无条件删文件。
