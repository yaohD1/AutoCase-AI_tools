# 2026-11-02 等待加载 + 点击跳转落点

用户：「缺一个智能等待直到页面元素全部加载，现在只支持固定等待多少秒，实际使用频率不高」。
中途他引 Playwright 文档反问「page.waitForLoadState() 做不了吗」，最后给了真实场景：
**一个操作点击后页面跳转，网络慢，页面没立即加载，下一步直接没定位到元素**。

## 结论：这行 API 能做，但只治一半

- `waitForLoadState('load')` 等的是**下一次 load 事件**：`The navigation must have been committed… If current document has already reached the required state, resolves immediately.`
  （本地 `.venv/.../playwright/sync_api/_generated.py` 原文）
- 所以：跳转类有效；SPA 换路由、点保存后异步刷列表、骨架屏出数据 —— **调用即返回**，等于没写。
- `networkidle` 官方标 DISCOURAGED（500ms 无连接），遇轮询/埋点/长连接会等满超时。
- 跳转那档我们本来就等：`page.goto()` 的 `waitUntil` 默认就是 `'load'`，回放器也是 `wait_for_load_state()`。
- 三个方案（A 手动插一步 / B 录制时自动插 / C 现场实测填参）用户没选，直接给了场景，
  于是按场景落地成「一步手动 + 一步自动」。

## 落地的两件事

### 1. `page_ready` 意图（工具栏「等待加载」）

- IR 只加常量：`PAGE_READY` / `READY_STATES = ('load','domcontentloaded','networkidle')` /
  `DEFAULT_READY_SECONDS = 15`；`step_type_for_intent('page_ready')` 固定回 `wait`。
  **没有新增 step 类型**——时间线渲染、上移下移、拖拽、回放全按 `type` 分叉，加一个是改一圈。
- 它**不进 `INTENT_TYPES`**：那是自然语言解析的词表，模型会顺手把「等元素出现」也塞进来。
  这一档只由工具栏给，`intent.validate` 单独放行。
- `validate`：`state` 越界报错；`timeout` 缺省 15、给 0 也回到 15（0 秒 = 必然失败，不能当成"不等待"）；
  不接受 `reload`（刷新会重置这次导航的加载状态，越刷越等不到）。
- 生成：Playwright `await page.waitForLoadState("<state>", { timeout })`；RF 用
  `Wait For Condition    return document.readyState === "complete"`，`domcontentloaded` 用 `!== "loading"`。
- 回放：`replay._assert_once` 直接 `page.wait_for_load_state(...)`，同口径（已 load 完立刻返回）。
- 前端：工具栏第四颗按钮 + 草稿卡（三段 load/DOM/idle + 最多等 N 秒 + 一行 note）。
  分段里用短名，面板只有 420~600px，`domcontentloaded` 全名会把三档挤爆。
- 超时算**失败**（用户同意）：等不到就是页面没起来，继续跑只会更乱。

### 2. 点击引起的跳转落点 `nav_to`

- 录制侧原本就把「点击引起的跳转」吞掉不记 goto（`_clicked_recently`）。现在多一步：
  `_mark_click_nav(url)` 把落点写到触发它的那条 click 上，回看三步、能跨过 `new_page`。
- 生成提示词两套框架都加了一条：带 `nav_to` 的点击后面补 `waitForURL("**" + 路径)` /
  `Wait Until Location Contains`。只取路径，不写死查询串。
- 前端步骤行显示 `→ /home?tab=1`（`.step-nav`），解释脚本里那行 waitForURL 不是凭空多出来的。
- 这条是**零操作**的：用户不用插步骤，录制时点一下就自动带上。

## 不唯一 → 必选弹窗 + 按下那一刻的截图

用户原话：「这个功能太冗余了，我选择完成之后现在是在工具栏提醒我选择，这种不要当成提醒，
改成直接醒目弹窗必选」+「点不唯一的按钮导致页面变了，现在有个回到当时页面的功能，我用了不好用，
能不能直接截一张图、图上框选、在弹窗里确认，不用动录制页面」。

选定：A 按下鼠标就截（不是点完再截）/ 只挡面板不暂停 / 只截视口。

### 关键时机

- `precount` 是 pointerdown 发的，比 click 和跳转都早 —— 截图放这里才截得到「原来那一页」。
  点完再截，跳转类只能拿到新页面甚至白屏，而那正是最需要图的场景。
- 只在 `_collect_matches` 返回非空（真的不唯一）时截，唯一的那几百次点击不付 50~80ms。
- 图存 `self._shots[shot_id]`（内存，最多 40 张），`target.shot = {id, w, h}`；
  `GET /steps/<no>/shot` 按步骤号取（id 挂在 target 上，步骤重新编号也不受影响）。

### 三个坑

1. **图上的尺寸必须是 CSS 像素**：有头浏览器 `page.viewport_size` 是 None；PNG 的像素尺寸
   又含 devicePixelRatio。改成从 PNG 的 IHDR 读宽高（字节 16/20，大端）再除以 dpr。
   不折回 CSS 像素的话，125% 缩放的机器上框整体偏小一圈。
2. **`locator.click()` 写测试会丢截图**：它把 down/up 挤在一起，precount 那条 binding 还没到
   Python，页面就被 click 带走了（表现为所有候选 count=0、状态 stale/unverified）。
   测试里改成 `mouse.down()` → 停 100ms → `mouse.up()`。真人点击天然有这段间隔。
3. **有截图就别再调 `highlight`**：它会 `scrollIntoView`，等于替用户把被测页面滚了，
   那正是「回到刚才那页」难用的根源。有 shot 时直接跳过整条实时框选。

### 交互

- 右上角浮层（`.loc-confirm`）换成 `el-dialog.loc-dialog`：没有关闭按钮、点遮罩和 Esc
  都不关，出口只有「就这个，继续」和「不看这个，允许降级」。
- 降级落 `target.degraded`，`blockers` / `needsLocConfirm` / `reviewable` 三处都放过它，
  不再反复弹。后端 `_degrade_now` + `POST /steps/<no>/degrade`。
- 工具栏那颗「N 处定位待确认」的提示删掉了；生成时若还有 blockers，不再是「确认框放行」，
  而是把那几步排队弹出来，选完才能写。
- 图上框：`getBoundingClientRect` 顺手塞进 `MATCH_SUMMARY_JS` 的 items（x/y/w/h），
  前端按百分比定位，弹窗宽度和图片缩放怎么变都对得上；视口外的元素不画框，列表标「不可见」。
- 编号做成实心小方块压在框左上角：细框在浅色页面上几乎看不见，有实心块才数得清几个。

## 「截图看不清 A 和 B」——是缩放比例，不是没截到

用户第三次提这个（前两次「截图方案不实用」都被打断），这次给了准确描述：
「截出来图看不清到底 A 和 B 对应的页面哪个元素」。

### 根因

整页 1920px 压进 500px 的框是 **0.26 倍**：24px 的图标只剩 6px，两个挨着的同名按钮
连同框一起糊成一团。之前一直在调样式（居中、留白、失败文案），调错了地方。

### 方案（用户选 A+B 组合，纯前端，后端 0 改动）

- **A 聚焦**：`focusRect` = 候选并集 + pad 44 → 宽度下限 150px（= 放大倍数，画布 460/150≈3x）
  → 比例夹进 [1.15, 3.0] → 夹回图内 → 占比 >90% 退回整页。
  实现是两层：`.shot-stage`（画布，宽高比=聚焦框）+ `.shot-inner`（整张图，位置/尺寸全百分比），
  框的百分比定位一个字都没改。
- **B 证件照**：同一个 PNG 当放大镜，`thumbScale = min(1, 46*0.78/item.w)`，最多 1:1；
  圈只描边不填色。屏幕外的标「屏外」。
- 字母 A/B/C（数字在缩略图上只有 5px 高）；徽标上方有 20px 就挪到框外，不压字。
- 悬停联动：指哪行/哪个框就加粗，其余 opacity .3。

### 坑

- **`is-origin` 不能铺 `var(--warn-soft)`**：会把元素文字整块盖掉，等于没截。改 2px 琥珀边 + 7% 底。
- 窄屏（≤900）`.dlg-viewer` 固定 280px，聚焦后是条横带 → 上下各留一大块灰。
  覆盖成 `height:auto` + `.dlg-stage{flex:none}`。
- 只有宽度设下限：给高度兜「至少四分之一屏」会把一行按钮压成半屏白。

### 验证

- `shots/_check_loc_dialog.py`（真实 1139×738 截图，4 个 tab）：zoom 2.41，框 87px 对应 88px 原尺寸（≈1:1）。
- `shots/_check_loc_focus.py` 四种形状：两个 18px 图标放大到 56px（3.1x）、
  散在四角时 zoom=1 退回整页、上下两行不被压成细缝、滚出视口那条标「屏外」且不画框。
- 深浅色两套都看过；无图分支留 18px 内边距。

## split 模式两窗口：无壳 + 贴齐 + 粘住

用户：「开两个倒是无所谓，但视觉上和易用性上都不好」→ 选了 A（无壳并排），
追问「能不能让两个窗口紧紧贴在一起，像用胶水粘住」。

### 做了什么

- 面板窗口改 `--app` 起独立浏览器（无标签栏/地址栏）+ 独立临时 profile。
- 用**系统 Edge** 而不是 Playwright 的 Chrome for Testing：CfT 顶部必挂
  「仅适用于自动测试」横幅，`--test-type`、`--disable-features=ChromeForTesting`
  都关不掉（v148 实测）；Edge 需再加 `--disable-sync --no-service-autorun`
  压掉「同步你的浏览数据」弹窗；`--ignore-certificate-errors` 只在 https 面板 URL 时加，
  否则会挂黄条。
- `layout_windows` 改按**显示器工作区**（扣任务栏、多屏跟着窗口走），0 缝隙。
- 新增 `winwindows.py`：可见边界、工作区、按 pid 找窗口、粘合。
- 删除「8px 缝」旧逻辑；`sheet_windows` 支持无壳面板（先解粘合再铺宽）。
- 面板页 title 改「AutoCase 录制面板」，Alt+Tab 能跟被测站分开。

### 关键发现（最重要的一条）

**接缝那条黑带不是阴影，是 `GetWindowRect` 的不可见拉伸边框。**
Win10 每个窗口左右各 8px 是 resize 边框，`GetWindowRect` 算进去但看不见。
所以「矩形贴死」视觉上漏 16px，露出的是桌面壁纸。
正解：`DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` 拿可见边界，
对齐可见边界后再反推回窗口矩形。实测缝从 18px 黑带变成 2px 细线，
而且**不遮内容、不吃滚动条**（我一度打算重叠 20px 来盖住缝，那会吃掉右边缘）。

### 粘合的三个坑

1. 钩子必须装在**收消息的那个线程**。装在主线程、去别的线程 GetMessage，事件 0 条。
2. 不能用布尔标志防乒乓：OUTOFCONTEXT 回调是异步投递的，等它跑起来标志已清。
   要记住「我刚把它放到哪」，收到正好落在那儿的同一事件才认定是自己干的。
3. `idObject != OBJID_WINDOW` 要跳过，否则子控件移动也触发。

### 清理坑

Edge 的启动器把活交给真正的浏览器进程后自己就退出，`Popen.terminate()` 是空操作
→ 桌面留一堆面板窗口（实测残留 7 个）。必须 `taskkill /F /T /PID <窗口所属进程>`，
再加 `atexit` 兜底。

### 验证

- `shots/_check_split_windows.py`：可见区 main(0,0,1114,1030) / panel(1114,0,806,1030)，
  缝隙 0、顶差 0；移动 main +120/+40 → panel 跟 (120,40)；移动 panel +60 → main 跟 (60,0)。
- `shots/_check_window_glue.py`、`_check_seam_measure.py` 是过程验证（含「矩形贴死 vs
  可见边界贴齐」的亮度扫描对比，18px → 2px）。
- 新增 `test_recording_window_pair.py` 7 条（工作区切分、无缝、面板最小宽、无面板/无头不动手、
  粘合失败不影响录制）。全量 561 条通过 + 新增 7 条；`npm run build` 通过。

## 拖接缝：不能只搬位置（用户实机反馈的 bug）

用户原话：「我去拖动粘合边 怎么非粘合边也会往那边靠啊」。

`Glue._on_event` 里 `SetWindowPos(dst, 0, nx, ny, 0, 0, SWP_NOSIZE)` —— 只同步位置、
**从不同步尺寸**。于是拖接缝 = 把对面整个推走：推 A 的右边 → B 平移 → B 的右边也跑，
整对窗口像积木一样被推来推去，外侧那条边跟着漂出屏幕。

### 正解：区分「平移」和「拖边」

比 src 前后两条边的位移：
- 两条边位移**相等** → 整体平移，照搬位移、尺寸不动。
- **不相等** → 拖的是某一条边，接缝跟着走，对面从**靠缝那侧**伸缩，**外侧边钉死**。

抽成纯函数 `winwindows.plan_follow()`，不碰 Win32，8 条单测直接覆盖。

### 三个配套细节

1. **高度要跟 src 一致**，否则拖完两条下沿是锯齿；
2. 对面压到 `SPLIT_MIN_W/H` 时把被拖那条边**推回来**（`src_fix`），不然接缝裂开；
3. 回声判定从「严格相等」放宽到 **4px 容差**——窗口管理器会取整、窗口也有自己的最小尺寸，
   严格相等会漏判，把自己的一次摆位当成用户拖动，两个窗口对推。

### 验证（`shots/_check_split_seam.py`）

- 拖 main 右边 +120：main 1114→1234，panel 1114→1234（宽 806→686），
  **main 左 0 不动、panel 右 1920 不动**，接缝差 0。
- 拖 panel 左边 −100：panel 左 1234→1134（宽 686→786），main 1234→1134，
  **main 左 0 不动、panel 右 1920 不动**，接缝差 0。
- 整窗口平移 +90/+30：两边都移位、尺寸不变（没被改坏）。
- 极限 +600：panel 卡在 360，main 右边被推回到 1650，接缝差 0，1.6 秒后再测位置不变（无抖动）。
- 单测 `PlanFollowTest` 8 条 + 原有 7 条；全量录制测试见下。

## 「并排」按钮点完没排好（用户实机反馈）

用户原话：「这个并排按钮是干嘛的 点击就变成这样子了」（截图：两个窗口挤在左侧，

### 根因一：兜底路径谎报成功

`layout_windows()`：

```python
if self._layout_native(): return True          # 原生路径失败 →
...
self._set_window_bounds(main, ...)             # CDP 只摆得了被测窗口
if self._panel_page is not None: ...           # 无壳面板这里是 None！
return True                                    # ← 照样报成功
```

无壳面板是**另一个进程**的 Edge 窗口，CDP 根本够不着。于是「被测窗口挪了一下、
面板原地不动」，前端却弹「已重新并排」。现在：`_panel_page is None` 时直接返回 False，
界面说「无法调整窗口位置（可能已被关闭或系统拒绝）」。

### 根因二：最大化把原生路径整条跳过

`_layout_native` 开头 `is_usable(panel)`，最大化 → False → return False → 掉进上面的兜底。
用户的典型动作正是「先最大化看完，再回来点并排」。新增 `winwindows.prepare()`：
先 `ShowWindow(SW_RESTORE)`，轮询等它真的变回普通窗口（≤0.6s）再摆。

### 根因三：还原后的第一遍摆位差 90px

还原那一刻窗口边框从「最大化无边框」变回「左右各 8px 拉伸边框」，
`move_visible` 读到的还是旧边框 → 请求 806 实际摆成 896，面板右边界跑出屏幕。
改成摆完用 `_pair_is_flush()` 校验（被测窗口位置 / 两窗宽度 / 接缝 0），
不对就再摆，最多 3 遍（每遍之间 50ms 让边框稳定）。

### 验证（`shots/_check_split_seam.py` 新增两项）

- 最大化面板 → `relayout` → 面板 `IsZoomed=False`，main (0,0,1114,1030) /
  panel (1114,0,806,1030)，接缝 0（修之前是 896 宽，右边出屏）。
- 杀掉面板进程 → `relayout` → `{'laid_out': False}`（修之前是 True）。
- 单测新增 `test_restores_maximized_windows_before_laying_out`、
  `RelayoutFallbackTest.test_shell_less_panel_never_reports_false_success`。
